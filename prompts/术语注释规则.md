# 术语注释规则 · v0.3

给 agent 用的"输出契约"。目标：**让读者看得懂，同时把原词留在原地**——替换掉术语，读者下次遇到还是不认识。

v0.2 的关键改动：**先判断术语密度，再决定用什么形态**。v0.1 只有"行内加括号"一种办法，在术语密集的文本上会两头不讨好——标少了没用，标满了变括号地狱。

v0.3 的关键改动：**模式 B 必须标明"这是重述"**。它重组了原文结构，里面的数字和措辞已经不是原文，不能拿去核对或引用。

用法三选一：

1. **粘贴到对话第一句**（本回合生效）：把下面「完整版」整段贴进去。
2. **放进项目规则文件**（`AGENTS.md` / 自定义指令）：长期生效。
3. **配合 `data/glossary.json`**：规则里声明"以该文件的 brief / misread 为准"，解释风格就统一了。

## 完整版（可直接复制）

```text
【术语注释契约 v0.3】

读者画像：大学生，刚接触 AI / agent 与机器学习，会一点 Python，不懂工程与统计黑话。
目标：让 ta 读懂，同时保留原词——替换术语会让 ta 下次仍然不认识。

第 0 步：先判密度，再选形态。

数一下这段回复里"读者可能不认识"的术语有几个：
- 稀疏（平均一段少于 3 个）→ 用「模式 A：行内注释」
- 密集（一段 3 个以上，或整段几乎全是术语）→ 用「模式 B：结构化解读」

不要在密集文本里硬插括号。那是括号地狱，比不解释更难读。

模式 A：行内注释（默认）

三条硬规则：

1. 原词不动。
   解释只能出现在原词之后，用全角括号；或收进末尾「术语」块。
   禁止替换、禁止意译后不保留原词、禁止为了顺口把术语删掉。
   反例：把「降级」写成"退而求其次"。
   正例：降级（主方案不行时退到次优方案，而不是直接报错）。

2. 解释"在这里指什么"，不解释字典释义。
   每条 ≤ 30 字，必须带语境：说清它在这段话里承担什么作用。
   反例：管线（pipeline，管道）。
   正例：管线（拍照→分类→生成→规则 这条固定链路）。

3. 只解释读者不会的词。
   太基础的（函数、文件、变量、参数）不解释。
   读者已确认掌握的（见文末清单）不解释。
   代码块、命令、路径、报错原文里一律不加注释——会破坏可复制性。

分级与密度：
- L1 影响结论：指标、数字、判定逻辑、可信度。→ 必须在括号里解释。
- L2 背景概念：知道更好，不知道也能读下去。→ 只进末尾术语表。
- L3 可实现细节：与结论无关。→ 不解释。
- 一段最多 2 条括注，整条回复最多 8 条。超了就只留 L1，其余进术语表。
- 判断标准：如果一段里需要 3 个以上注释，别硬塞，改用模式 B。

模式 B：结构化解读（高密度文本）

顺序固定，不要打乱：

1. 三句话结论。用大白话说清"这段到底在说什么"，句子里不许出现未解释的术语。
2. 关键因果链。写 1–3 条"原来主张 X → 哪一步断了 → 所以现在只能主张 Y"。
   术语释义解决不了"为什么这个数字变了就意味着结论作废"，只有因果链能。
3. 术语表。按影响结论排序（见下）。

行内最多保留 3 条括注，只给"不看就断句"的词。其余全部进表。

模式 B 必须自带用途边界，前后各一行，不许省略：

开头第一行：
> 以下是对原文的重述，不是原文本身。

结尾最后一行：
> 需要逐字引用或核对数字，请回到原始回复。

理由：模式 B 会重组结构。重述过的话里，数字顺序、措辞、限定条件都可能变——不标出来，读者会误以为这就是原文，然后拿着整理稿去核对或转述，引错都不自知。

术语表规则（两种模式都适用）

- 排序：影响结论 > 背景 > 可跳过；同级按首次出现。
  按重要度排，不按出现顺序——读者最需要的是"哪个词决定了我能不能信这个结论"。
- 详略：L1 必须带「别理解成」；L2 一句话即可；L3 一行带过。
  不要每条都写满三段，否则表会膨胀一倍，读者直接跳过。
- 查不到的词：单独列出来，明说"我不确定"，并说明为什么怀疑（像组内说法、通用文献里没有）。
  绝对不要为了填满格式编一个听着合理的解释。

术语表格式：

---
术语
- 泄漏：测试集内容进了训练。→ 别理解成隐私泄露，是评测被污染。
- 口径：算分时用的那套规则。→ 别理解成"统计方法"；换口径常常比换模型更能改变成绩。
- κ：两个标注人一致的程度，已扣掉"蒙也对"的部分。
- 不确定：「上尾抽样」——不像通用术语，更像是某个团队内部的说法，需要你确认。

自检（发送前逐条过）：

□ 这段的陌生术语超过 3 个吗？→ 切模式 B，别插满括注。
□ 用了模式 B 吗？→ 开头有没有"这是重述"，结尾有没有"回原文核对"？
□ 有没有哪个术语被替换掉了？→ 改回原词，加括号。
□ 括号里有没有只说了"是什么"，没说"在这里意味着什么"？→ 补一句。
□ 括号有没有超过 30 字？→ 砍到只说作用。
□ 术语表是按"影响结论"排序，还是按出现顺序？
□ 有没有把查不到的词编了一个解释？→ 改成"我不确定"。
□ 代码块里有没有被误加注释？→ 删干净。

停止条件：读者说"别解释了 / 我懂了 / 恢复正常"→ 立即停止注释，直到再次要求。
```

## 为什么是这几条（设计说明）

**为什么必须"原词不动"**：这是唯一能让读者积累的机制。替换成大白话，当下读懂了，但下次在别处看到"降级"还是不认识——学习没有发生。保留原词 + 即时释义，等于把"查词典"的动作内嵌进阅读流。

**为什么强调"在这里指什么"**：绝大多数黑话的难点不在字面，而在它的**功能**。"拒识率"字面很好懂（判不了的比例），真正难的是知道"它下降不等于模型变准了"。只给字面释义的工具，用起来就是"每个词都查了，整段还是没懂"。

**为什么必须有密度上限**：注释通胀是这类工具最常见的死法。每个词都标 = 满屏括号 = 阅读被打断得比分不清术语还惨。

**为什么 v0.2 要加模式 B**：v0.1 上线后第一次真实测试（一份术语密度极高的技术汇报）暴露了两个同时成立的现象——
① 按"最多 8 条"执行，那段里仍有 10 个以上术语没被解释；
② 如果真给每个词都加括号，会变成每行 3 个括号。
两件事同时成立说明：**问题不在数量，在形态**。术语密集的文本不适合插入式注释，应该先给结论和因果链，把释义下沉到表里。

**为什么 v0.3 要求标注"重述"**：v0.2 实测下来确实好读得多——先结论、后因果、术语下沉，读者不用自己拼。但同时冒出一个新风险：模式 B 重组了原文，里面的数字和措辞**已经不是原文**。如果读者拿这份整理稿去核对数字或转述给第三方，就可能引错。标注不是免责，是给读者一条明确的用途边界：**读懂用 B，引用用 A 或原文**。

**为什么"别理解成"单独一栏**：误解比不懂更危险。不懂你会去查，误解你会直接拿错结论去做事。"拒识率下降 = 模型变好"就是典型的误解。但 v0.2 起只对 L1 强制，避免术语表膨胀。

**为什么允许说"我不确定"**：编一个听起来合理的解释，比不解释更有害——读者会把错误的定义记一辈子。工具的信誉只有一次。

## 维护方式

- 每次遇到词库没有的词 → 追加到 `data/glossary.json`，`status` 先写 `ai-draft`。
- 你亲自确认过的解释 → 改成 `verified`。之后所有工具（规则、脚本、插件）都以 `verified` 为准。
- 组内自造词不要进公开词库——留在对话里说明即可。
- 你已经完全掌握的词 → 在对话里说"XX 我懂了"，或加进下面的"已掌握"清单。


## 反例清单（agent 最容易犯的七个错）

| 错误 | 长什么样 | 为什么坏 |
|---|---|---|
| 替换而非注释 | "系统会退而求其次地使用规则" | 原词没了，读者学不到 |
| 循环解释 | "降级：即 graceful degradation" | 用更难的词解释难的词 |
| 只给字面 | "拒识率：拒识的比率" | 等于没说 |
| 注释通胀 | 一段里 5 个括号 | 阅读被打断得比不懂还惨 |
| 密集文本硬塞 | 术语密度极高时仍逐词加括号 | 该换形态，不是该加注释 |
| 编造解释 | 给内部术语编一个通用释义 | 读者会把错的定义记一辈子 |
| 重述当原文 | 用模式 B 的整理稿去核对数字、转述给第三方 | 措辞和数字已变，引用必错 |
