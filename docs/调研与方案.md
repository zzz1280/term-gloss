# 让 agent 说人话：技术黑话即时注释工具的调研与方案

> 目标读者：刚接触 AI / agent 领域的大学生。
> 核心约束：**解释术语，但不替换原词**——保留原词是为了"边用边学"，替换掉就学不会了。

---

## 一、结论先行

1. **开源社区没有现成的、完全对得上的项目。** 有四类半成品零件，但没有一个同时满足「自动 + 保留原词 + 针对 agent 回复 + 可沉淀成术语库」。
2. **最该做的不是"选一个形态"，而是先分清三层。** 这个需求实际上混着三个不同的问题：
   - **识别**：哪个词算黑话？（词典能查 vs 只能靠上下文猜）
   - **呈现**：解释放在哪儿？（括注 / 悬停 / 末尾词汇表）
   - **记忆**：见过的词怎么不重复解释、怎么复习？（术语库 + 生词本）
   形态选择只是第二层的事。三层拆开之后，"浏览器插件 vs 脚本"这种纠结会自动消解——因为它们各自只擅长其中一层。
3. **推荐组合，而不是单选：**
   - 今天就能用（0 成本）：**输出契约（提示词/规则）**——让 agent 每次回复时"原词 + 括注 + 末尾术语表"。
   - 一周内（半天到一天）：**本地脚本 + HTML 阅读器**——把回复变成可悬停、可收藏的页面。这是术语库的"生产车间"。
   - 长期（如果真天天用）：**只做注解层的浏览器插件**——不改正文，只外挂一层可开关的注释。
   - 补位：**桌面划词工具**覆盖 IDE / 终端 / PDF（`ai-jargon-translator` 已验证这条路，并明确得出"浏览器插件不该是第一主线"的结论）。
4. **一个必须现在就定死的架构决策：让模型输出「术语 + 位置 + 解释」的结构化数据，由前端渲染，绝不让模型重写正文加括号。** 否则原文被改、无法折叠、无法统计，而且模型一旦顺手改写了别的内容，读者就失去了判断它是否可信的依据。这条是本方案和现有项目最大的分歧点。

### 2.1 找到的相关项目（按与本项目的相关度排序）

### 2.2 三条有用的调研结论

- **"词表 + 虚线下划线 + 悬停浮层"是被反复实现、被验证过的交互**（word-tips、ai-jargon-translator、jekyll 插件、auto-glossary 各自独立做了一遍）。它成立的原因很朴素：不打断阅读、不改原文、可关闭。这是注释层的默认答案。
- **"让模型直接改写正文加括号"是主流做法，但在本场景里是错的**（Innline Annotation 就是这么做的）。因为这里要的是**学习**：一旦原文被改，读者就分不清哪句是 agent 说的、哪句是工具补的；而且括注不可收起，长回复会变成括号地狱。
- **提示词层的项目全都选择了"替换"而不是"保留"**。这不是他们没想到，而是因为"保留 + 注释"在纯文本界面里无法优雅表达——纯文本没有悬停。**这正是需要一个渲染层的原因。**

### 2.3 空白点

没有任何项目做到：**面向 agent 回复、自动标注、保留原词、注释可开合、并把"我见过的词"沉淀成个人术语库**。
要做的东西是新的，但每个零件都能捡现成的。

## 三、需求拆解：三个断层

| 断层 | 表现 | 该由谁解决 |
|---|---|---|
| **识别断层**：不知道哪个词是"术语" | "预写判据"这种就地造词，词典查不到；"管线""降级"这种通用词，词典能查到但不知道此处指什么 | 词典（稳定、可解释）+ LLM（补新词、结合上下文）+ "已掌握"标记 |
| **理解断层**：看懂了字面，不知道它在这句话里意味着什么 | "拒识率从 12.4% 降到 8.1%"——数字看懂了，但不知道这是好事还是有诈 | 解释必须带 **"为什么在这里出现"**，不能只有词典释义 |
| **记忆断层**：下次又忘了，或者被反复解释同一个词 | 第 1 次见"领域偏移"要解释，第 10 次还解释就是噪音 | 术语库 + 计数 + 掌握度，**只对"未掌握"的词注释** |

大部分同类工具只解决第一层（词表查义），所以用起来"懂了但没完全懂"。这个工具如果每条注释都带"为什么这里会出现 / 别理解成什么"，价值会高一档。

## 四、五种实现方案

### 方案 A：输出契约（提示词 / 规则文件）——让 agent 自己注释

**做法**：在系统提示或项目规则里写死三条：
1. 术语保留原词，首次出现时用**全角括号**给一句话解释（≤ 25 字），不替换、不删词。
2. 一段最多 3 条括注；不影响结论的词只进末尾术语表，不插正文。
3. 回复末尾固定一块「本文术语」，只列**本文出现过且读者尚未确认掌握**的词。

**成本**：0。半小时调措辞。
**优点**：唯一能覆盖**所有**场景的形态（网页聊天、IDE、CLI、手机）；不装任何东西；解释天然带上下文（模型知道"这里"指什么）。
**缺点**：**遵守度是概率性的**——长对话会漂移、复杂任务里顾着干活就忘了；纯文本里括注只能"摊开"，无法收起；解释当场生成，可能编（尤其对"预写判据"这种内部词，模型可能顺着上下文瞎圆）；无法沉淀（下次还得再解释一遍）。
**适用**：作为兜底和第一层，不要指望它是最终形态。

### 方案 B：浏览器插件（只做注解层）

**做法**：content script 监听 AI 聊天页（ChatGPT / Claude / DeepSeek / Kimi 等）的消息节点，把回复文本交给"词典 + LLM"得到**结构化注释表**（术语、字符区间、一句话解释、为什么在此出现），然后在 DOM 里用 `Range` 把命中的词包一层 `<span class="gloss">`，虚线下划线 + 悬停/点击浮层。**正文一个字符都不改。**

**成本**：1 天出可用的单人版；做好 3 天。
**优点**：交互最好（不打断、可开合、可一键"全部展开"对照读）；能统计"这个词我查过 5 次"；能顺手做生词本；隐私可做到"只在本机调用户自己的 key"。
**缺点**：**覆盖面最窄**（IDE 里的 agent、终端、桌面客户端全都不管）；各家聊天页 DOM 结构不同且会改，选择器要持续维护；流式输出时节点反复重排，实现要小心（**绝对不要直接改 innerHTML**，会破坏 React 状态，要用 Range 包裹或旁挂 overlay）；对不装扩展的同学零可用性。
**适用**：主要在网页版聊天里读回复时。

### 方案 C：本地脚本 + HTML 阅读器

**做法**：`gloss.py reply.md` → 输出 `reply.gloss.html`：原文本逐字保留，命中的术语包成可悬停的 span，右侧或底部给术语表，支持"仅显示首次出现 / 全部展开 / 关闭"。注释表缓存在 `glossary.json` 里，同一个词第二次出现直接命中，不再调模型。

**成本**：半天。
**优点**：**可行性最高、最不容易坏**（不依赖任何第三方 DOM；不需要 API key 也能用纯词表跑）；原文 100% 保真，天然适合"存档 + 复盘"；批量处理历史会话很方便；是**术语库的生产车间**——在流程里确认过的解释，之后可以直接喂给插件和提示词。
**缺点**：不是"每次回复即时"，要多一步复制粘贴；交互弱于插件；不适合手机。
**适用**：复盘、批量整理、积累术语库。**建议第一个动手做的就是它**，因为它产出的 `glossary.json` 是所有其他形态的共用地基。

### 方案 D：桌面划词工具（全局快捷键）

**做法**：常驻托盘，选中任意窗口里的词 → 双击 Ctrl → 置顶小窗给解释（本地词库优先，未命中再调模型）。

**成本**：1~2 天（Python + pyperclip + pynput + tkinter，或用 Tauri 做得好看点）。
**优点**：**覆盖最广**（IDE、终端、PDF、桌面 agent、甚至别人的 PPT）；零误报（查哪个词由人决定）；隐私最好；离线可用。
**缺点**：**手动**——"边用边学"退化成"边查边学"，读到一半要打断去查，正是要避免的那种断线；Windows 取词靠复制剪贴板，会污染剪贴板；打包/签名有琐碎麻烦。
**适用**：兜底查询工具，或直接先用现成的 `ai-jargon-translator` 顶着。

### 方案 E：本地代理拦截 API 流（**不推荐**）

**做法**：本地网关拦 SSE 流，边收边改写，再转发给客户端。
**缺点**：流式分块会把词切断（一个词可能横跨两个 chunk）；各家协议不同；证书/代理配置劝退；一旦出错整个对话不可用；隐私风险最高。**投入产出比最差，除非要做商业产品。**

## 六、推荐路线

### L0（今天，30 分钟）：输出契约 + 一份最小词表

在规则里固定这套行为，并附上已确认掌握的 20~30 个词（避免重复解释）：

> 回复中的技术术语**保留原词**，首次出现时紧跟全角括号一句话解释（≤25 字，说"在这里指什么"，不是背词典）。每段最多 3 条。只在影响结论时才插括注，其余进末尾「术语」块。已掌握的术语不解释。

产出物：一段可复用的提示词 + `glossary.json`（先手写 30 条踩过的词）。

### L1（一两天）：脚本 + HTML 阅读器（**核心建议**）

- 输入：剪贴板或 `.md` 文件；输出：带悬停注释的 HTML。
- 识别：**词典优先**（本地 JSON，正则最长匹配）→ 未命中再让模型补，补完**写回词库**。
- 呈现：原文不动 + 虚线下划线 + 悬停卡片（术语 / 一句话 / 为什么在此 / 别理解成）+ 开关（全部展开 / 仅首次 / 关闭）。
- 副作用：`glossary.json` 越来越厚，命中率越来越高，**模型调用越来越少**——这是这套方案能长期活下去的关键。

### L2（可选，一两周）：浏览器插件（只做注解层）

- 只监听常用的 2~3 个站点，先做 DeepSeek / Kimi / ChatGPT。
- 用 `Range` 包裹或 shadow DOM overlay，**不改 innerHTML**。
- 与 L1 共用同一个 `glossary.json`（通过本地服务或 `chrome.storage` 同步）。

### L3（补位）：桌面划词

先直接用 `ai-jargon-translator`；不满意再自己写，或做成 Tauri 小工具。

## 七、四个必须提前定死的技术决策

1. **模型输出结构化注释，不输出改写后的文本。**
   schema：`{term, start, end, brief, why_here, misread, level}`。
   好处：原文零改动、可折叠、可统计、可校对、可缓存。坏处：要处理字符偏移对齐（中文按 UTF-16 码元算，别用 `len()` 数错）。
2. **词典优先，LLM 补位，结果回写。** 命中率是这套东西的生死线：纯 LLM 每条回复都烧钱且不稳定；纯词典遇到新造词就死。混合 + 缓存能同时解决。
3. **三种呈现分工，而不是三选一。**
   - 悬停：读的过程中查（默认）
   - 行内括注：需要"看懂这段"时全展开（一键）
   - 末尾术语表：复盘和复习
4. **解释分级，防止注释通胀。**
   - L1 影响结论（如"待定率""Macro-F1"）→ 必须解释
   - L2 背景知识（如"领域偏移"）→ 悬停有，不插正文
   - L3 可跳过（如"jsonl"）→ 只进词表
   一条铁律：**一段里超过 3 个注释，说明这段该重写，而不是该加注释。**

## 八、诚实的局限

- **LLM 给的解释本身可能是错的**，尤其是它没见过的内部术语（"预写判据"它很可能顺着上下文编一个合理说法）。建议：AI 生成 + 人工确认后才入库，入库后标"AI 释义 / 已校对"。
- **"保留原词"会降低可读性**，这是有意换取学习效果的代价。缓解办法是默认悬停、按需展开，而不是全部摊开。
- **自动判定"这个学生不懂"是不可能的**。任何工具都会误判（把已经会的东西也标上）。只能靠"已掌握"标记 + 频次衰减来收敛。
- **浏览器插件是最容易烂的形态**（DOM 改动、流式重排、站点适配）。如果不是天天在网页版聊天，不值得为它维护。
- **提示词层永远不可靠**。它会 80% 的时候做到，20% 的时候忘掉。所以它只能是兜底，不能是唯一。
